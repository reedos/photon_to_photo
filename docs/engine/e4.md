# Workstream E4: the camera model and the CPU reference renderer

`src/engine/data.ts`, `camera.ts`, `scenes.ts`, `render.ts`. Built after E1-E3 merged; this is the layer that
wires real `data/*.json` into the pure E1-E3 primitives (`data.ts`), turns a `Scenario` into a full `Model`
(`camera.ts`), builds the two named synthetic scenes (`scenes.ts`), and renders a low-resolution reference
photo from a `Model` (`render.ts`). See `docs/ENGINE.md` for where this sits in the whole engine and
`docs/BRIEF.md` for the project's accuracy discipline (every figure gets an evidence label; never invent a
number).

## data.ts

The one place engine data is imported; every E1-E3 module keeps taking its data as plain arguments, unchanged.

- **Glass**: `GLASS_CATALOG = makeCatalog(data/glass/catalog.json)`, built once.
- **Lenses**: `getRealizedLens(id)` / `getLensInfo(id)` run `loadLens` then `realize()` and cache the result
  per id (`realize()` costs on the order of 100 ms — see `realize.ts`'s own header — paid once per lens, not
  once per `compute()` call). `getLensInfo` also computes the DESIGN's own infinity-focus EFL once (distinct
  from `Model.cardinal.efl`, which is the CURRENT focus's EFL and can differ slightly for a floating-focus
  design).
- **Spectral bins**: `BINS`, built directly from `data/color/wavelength-bins-16.json`'s own edges/centers
  (identical to `spectrum.ts`'s `BINS16`, but traceable to that file rather than recomputed).
- **CIE data**: `CMF` (table-interpolated from the 1 nm CIE 1931 table), `V_LAMBDA` (= `CMF.ybar`), `D65_SPECTRUM`,
  the daylight `S0`/`S1`/`S2` basis tables.
- **ColorChecker**: `COLOR_CHECKER_NAMES`, `colorCheckerReflectance(name)`.
- **Camera spectral sensitivities**: `gaussianCameraSensitivities(peakQE)` (the default — see below) and
  `jiangCameraSensitivities(cameraName?)` (the measured, CC BY-NC-SA-licensed Jiang 2013 set, kept selectable
  but not used by default).
- **Sensors**: `sensorFor(format, iso, sensorId?)` returns `{ spec: SensorSpec, info: SensorInfo }` for one of
  the three real, cited picks in `data/sensors.json` (one per format), cached per `(sensor id, iso)`.

### The default camera-sensitivity model, and why

BRIEF.md's task text says to use the Gaussian model by default because the Jiang 2013 measured set is CC
BY-NC-SA and using it needs Reed's own decision. `gaussianCameraSensitivities(peakQE)` takes
`data/color/camera-sensitivity-gaussian-model.json`'s per-channel Gaussian fit (itself fitted to the Jiang
Nikon D700 curve, but carrying no license restriction — see that file's own note) and rescales all three
channels so the largest (G, whose source amplitude is already 1.0) peaks at `peakQE`, the sensor's own
reported peak-QE spec (`data/sensors.json`'s `qe.peakPercent`-family fields). Evidence: **derived** (a
reported spec combined with a shape fitted to a different camera). This is a real simplification — the true
per-channel QE shape of any of the three chosen sensors is not published (see `data/sensors.json`'s own
`openProblems`) — and is the honest option available, not a hidden approximation.

### Sensor data: read noise interpolated on Claff's own curve, not sensor.ts's two-level model

`data/read-noise.json` is Bill Claff's own measured read-noise-vs-ISO curve (photonstophotos.net), read
directly, not summarized. `sensorReadNoiseAtIso(cameraKey, iso)` log-log-interpolates between its points
(log2 ISO vs. log2 electrons, matching the scale the source chart itself plots in — the DCG step is a clean
corner there, not a near-vertical cliff). This is a materially better model of real read noise than
`sensor.ts`'s own `ReadNoiseSpec { lcgE, hcgE }` two-level step (which E3 built before per-ISO curves were
available in this project — see `sensor.ts`'s own doc comment on `ReadNoiseSpec`).

`sensorFor` still returns an ordinary `sensor.ts` `SensorSpec` (no change to sensor.ts — flagged in
`needs_from_lead` below), built **per ISO**: `readNoise.lcgE = readNoise.hcgE` = the interpolated value at
that exact ISO, and `dcgSwitchIso: 0` so `sensor.ts`'s own step logic is a no-op and always returns exactly
that number. `fullWellE` comes from the same `read-noise.json` record (Claff's own `fwc` field, internally
consistent with the read-noise curve it sits beside). `fullWellHcgE` (the DCG full-well change) is left
unset: no cited per-DCG-mode full-well figure exists for any of the three picks (again, `data/sensors.json`'s
own `openProblems`), and `sensor.ts`'s `fullWellAtIso` already falls back to `fullWellE` in both modes when
it is absent — the mechanism is wired, the number just is not invented where none is cited. Dark current is
extrapolated from each sensor's cited 0 C or -20 C cooled figure to a representative 60 C in-camera operating
point via the same doubling-temperature relation `data/sensors.json`'s own full-frame record already used
once (`extrapolateDarkCurrent`); black level (512 DN at 14-bit, scaled proportionally at other bit depths) has
no cited source and is labeled `assumed`, matching this project's own `fixtures/e3-sensor.ts` convention.

## camera.ts

`compute(scenario) -> Model` (`model-types.ts`'s contract), memoized by a JSON key of every `Scenario` field
(unbounded cache — fine for a prototype's realistic scenario-tweaking session; a long-lived server process
doing this would want an LRU instead). Plus `lensFans(model, req)` and `pointBundle(model, req)`.

### Normalization

`fno = max(scenario.fno, lens.maxFno)`. Focus: `closestFocusMm = realized.realization.closestFocusMm` (the
REALIZED closest focus — the larger of the design's stated minimum focus and what `focus.gaps` can actually
reach, per `realize.ts` — not `systemAt`'s own looser internal clamp against `design.focus.minFocusM` alone),
`clampedFocusMm = max(requestedMm, closestFocusMm)`, then `systemAt(lens, clampedFocusMm, { clamp: true })` as
the task brief asks. Passing the already-clamped value means `systemAt`'s own internal clamp is a no-op
(`clampedFocusMm >= closestFocusMm >= design.minFocusM*1000` always, by `realize.ts`'s own contract); `clamp:
true` stays on as the documented safety net.

### Front-principal-plane distances for DOF, and the size of the correction

`Model.focus.{hyperfocalMm,nearMm,farMm}` and the request distances `pointBundle` compares its `predictedBlurMm`
against are all converted between "from the sensor" (every `Scenario`/`BundleRequest` field's own convention)
and "from the front principal plane" (`dof.ts`'s own convention) via `distanceFromSensorToP`/
`distanceFromPToSensor`: `distFromP = distFromSensor + (cardinal.P - sensorZEffective)`. The offset
`(cardinal.P - sensorZEffective)` is exactly the "thick-lens difference" the task brief's own golden test
names — on p50 at 3 m focus it is on the order of tens of mm (well under the lens's own ~140 mm total length),
negligible against a meter-scale focus distance but genuinely nonzero; `camera.test.ts`'s DOF golden test
checks the gap against this exact offset rather than a fixed tolerance, so it stays meaningful at any focus
distance/lens combination.

### The exit-pupil-referenced blur diameter, and why it replaces a literal `dof.blurDiameter` call

`Bundle.predictedBlurMm` (from `pointBundle`) and `render.ts`'s own per-pixel defocus-blur sizing both go
through `exitPupilBlurDiameterMm(model, pointDistMm)`, **not** a direct call to `dof.ts`'s `blurDiameter`.
`pointDistMm` is the object's AXIAL distance from the sensor — the distance to its z-plane along the optical
axis, matching `types.ts`'s own "distances 'from the sensor' are what a camera's focus scale reads" convention
and `pointBundle`'s own `objectZ = sensorZEff - req.pointDistMm` two paragraphs down — never the Euclidean
distance to a specific off-axis point in that plane (see "Defocus-blur sizing" under `render.ts`, below, for a
caller that got this wrong for every off-axis pixel and was fixed).

`dof.blurDiameter`'s pupil-magnification correction scales the entrance-pupil aperture diameter by `pupilMag`
but keeps the SAME image-side conjugate distances the base (`pupilMag = 1`) formula computes — which are
implicitly referenced to the rear principal plane P2 (`thinlens.ts`'s own convention) — rather than to the
real exit pupil's own axial position. `blurDiameter`'s own doc comment names this directly: "This ignores the
... axial offset between the rear principal plane and the actual exit pupil ... see the module doc above for
when that matters." For most lenses at ordinary defocus distances that offset is small next to the conjugate
distances involved and the approximation is fine. It is **not** fine for p50 at f/2, defocused from a 3 m
focus to a 1 m point (the case `camera.test.ts`'s own golden pointBundle test uses): P2 and the real exit
pupil sit about 16 mm apart while the image-side conjugate distances there are only about 50 mm — a ~30% axial
mismatch — and `dof.blurDiameter` duly overshoots the real (ray-traced) blur diameter by about 35% in that
exact case (measured while building this test). Using the front principal plane's own conventional distances
instead of the entrance pupil (the module header's alternative suggestion) does not fix it either — the
dominant error is on the IMAGE side, which that suggestion does not address.

`exitPupilBlurDiameterMm` keeps the exact same physical model `blurDiameter`'s own doc comment derives — a
cone from a circular aperture of the exit pupil's own radius, converging toward the image of the in-focus
object, cut by the sensor sitting at the image of the defocused point — but plugs in the REAL exit pupil
(`Cardinal.xp.z`, `Cardinal.xp.r`) and the REAL paraxial image positions (`paraxial.ts`'s `imageOf`, already
tested elsewhere in this engine) instead of assuming the exit pupil sits at P2:

```
blur = 2 * xp.r * |imageOf(point).z - imageOf(focus).z| / |imageOf(point).z - xp.z|
```

Checked against real ray tracing (`camera.test.ts`'s pointBundle golden test) to within 5% on the exact case
above, against `dof.blurDiameter`'s ~35%. **`needs_from_lead`**: `dof.ts`'s `blurDiameter` could take an
optional exit-pupil z to fix this without reworking its API or its callers that don't hit this regime; this
workstream did not make that change itself since `dof.ts` is outside E4's own paths.

### `lensFans` / `pointBundle`

`lensFans` converts each `FanRequest.fields` fraction into a field angle (`fraction * realization.halfFieldDeg`)
and calls `trace.ts`'s `fan()` with `realAim: true`, once per field.

`pointBundle` builds an object-space `Field` at `pointDistMm` (from the sensor) and `fieldFrac` of the half
field, the same way `realize.ts`'s own field survey does (`o = [0, (objectZ - ep.z) * tan(angle), objectZ]`),
then calls `trace.ts`'s `spot()` with a `{ kind: 'fibonacci' }` pupil grid and `realAim: true`. `diameterMm` is
the landing points' max pairwise distance (a proper "max chord," not `2 * geometricRadius` — the two only
coincide when the centroid happens to be the true geometric center).

**A straight-bladed iris turns marginal on-axis rays away at some meridians even wide open.** `iris.ts`'s
polygon has its full circumradius only exactly at the `blades` vertex angles; a meridional ray fan (which
always samples the pupil rim at its two endpoints, per `trace.ts`'s `fan()`) generically lands at a
non-vertex angle for an odd blade count at `rotation = 0`, and that one ray is correctly turned away by the
blade there — real, expected polygon-iris geometry, not element vignetting (which `realize.ts`'s own on-axis
survey guarantees never happens on-axis). `camera.test.ts`'s "wide open, on axis" golden test checks for
exactly this: only `'ok'`/`'iris'` statuses on axis, never `'vignetted'`/`'tir'`/`'missed'`, and the chief
(center) ray always `'ok'`.

## scenes.ts

Two named scenes, `"bench"` (10,000 lux) and `"dusk"` (20 lux, otherwise identical), both 5500 K daylight
(`daylightAt(cctK)`, built from the real CIE `S0`/`S1`/`S2` basis via `scene.ts`'s own `daylightSpd`). Both
lux figures are round, **assumed** reference points (roughly "full daylight, not direct sun" and "deep
dusk/early night" respectively, per commonly-cited lighting/photography ranges) — no single fetched citation
backs the exact numbers, so they are labeled `assumed` rather than dressed up as `reported`.

Geometry: a ColorChecker billboard and a Siemens-star billboard both at the 3 m subject plane, a small
foreground object at 1.5 m, and a large backdrop at 25 m carrying four small point highlights (for background
bokeh). Sizes and offsets are chosen to frame reasonably on a normal-to-short-tele lens at these distances (a
very wide or very long lens will see mostly empty backdrop or a tight crop of one object — expected, not a
bug). The ColorChecker and the star are both kept well clear of the optical axis (near edges at about 4.3 and
8.5 degrees off axis respectively) so that an on-axis background highlight, and a modest search box around
it, are never contaminated by them — this matters for `render.ts`'s own "point highlight" golden test and for
any similar future probe of the frame center.

## render.ts

`renderImage(model, req) -> RenderResult`, pure and seeded. `renderSetup(model, width)` factors out everything
derived from `model` before tracing a single pixel (the sensor spec, `pixelScale`, the scene with the
scenario's lux/CCT override applied, etc.) and is exported for tests/tools that want to trace individual
sample points the exact way `renderImage` does.

### The binning scheme, honestly

A "rendered pixel" (the `width`x`height` grid `RenderRequest` asks for) stands for a `pixelScale`x`pixelScale`
block of REAL sensor pixels (`pixelScale = round(sensor.widthPx / width)`, forced even so a block is a whole
number of 2x2 Bayer quads). `raw[]` is still a Bayer mosaic at the RENDERED-pixel grid (`cfaColorAt('RGGB',
bx, by)` picks each rendered pixel's own nominal CFA color), and each rendered pixel's DN is that block's
**average** real pixel of that CFA color — not a sum. Concretely: `nSameColorInBlock` = `(pixelScale/2)^2` for
R or B, `2*(pixelScale/2)^2` for G (both Bayer positions), and each rendered pixel's raw DN is drawn from
`Normal(meanE, varianceE(meanE, ...) / N)` — the correct sampling distribution of the MEAN of N iid real
pixels (Poisson's own additivity would make an exact block SUM tractable too, but the mean is what stays in a
sane DN range and reads naturally as "what a binned/downsampled preview would show," which is the more useful
quantity for a viewer). `pixel(bx, by)` instead returns one fresh, independent, full-statistics REAL pixel at
the block's center (own mean, own seeded draw, via `sensor.ts`'s `samplePixel` directly) — this is what
BRIEF.md's binning ask requires ("pixel(x,y) must return the state of ONE real pixel ... so the loupe can dive
into a real pixel"). Both `raw[]`'s block sampling and `pixel()`'s single-pixel sampling draw from seeded,
disjoint `Rng` streams (`blockStream`/`pixelStream`, even/odd) so re-requesting the same seed is fully
deterministic and the two kinds of sample never share a stream.

### Rendering pipeline, per pixel

1. **Primary ray** (`traceSource`): a rectilinear pinhole projection from the sensor position and the
   lens's own current EFL (`dir = normalize([-x/efl, -y/efl, 1])`) — no lens distortion, no entrance-pupil
   offset, image inversion via the sign. BRIEF.md's own task text calls this "acceptable for the prototype."
2. **Scene lookup** (`scene.ts`'s `radiance()`): spectral radiance per bin and a hit depth (mm, straight-line
   from the sensor, matching `Scenario.focusM`'s own "from the sensor" convention for near-axis rays).
3. **Camera equation** (`exposure.ts`'s `imageIrradiance`, with cos^4 via the ray's own `cosTheta`): sharp
   (unblurred) image-plane irradiance per bin, then photons per bin for ONE real pixel
   (`photonsFromIrradiance`, the same final step `exposure.photonsPerPixelPerBin` takes, reimplemented
   directly since this module calls `imageIrradiance` itself before the blur splat and must not apply the
   camera equation twice).
4. **Channel collapse**: `sensor.ts`'s `expectedElectrons` against each of R/G/B's own QE curve, giving 3
   numbers per source pixel instead of 16 — QE-integration and spatial blur are both linear operators and
   commute, so pre-integrating per channel before splatting is exact, not an approximation, and is roughly
   5x cheaper per splat cell than carrying all 16 bins through the kernel.
5. **Blur kernel and splat** (BRIEF.md: "scattering each source pixel into its blur disk shaped by the iris
   outline ... energy-conserving"): defocus diameter via `exitPupilBlurDiameterMm` (see camera.ts, above),
   called with the hit's own AXIAL distance from the sensor (`src.objectPoint[2]` in the main loop; the
   highlight's own world `Z` in the point-highlight pass — see "Defocus-blur sizing" below, NOT `depthMm`,
   which is the ray's Euclidean hit distance) and
   diffraction diameter (`2 * airyRadius(550, workingFno)`) combined **in quadrature** (RSS) into one combined
   diameter — an assumed combination rule, not a true convolution of the geometric and Airy PSFs (which this
   prototype does not compute) — then rasterized against the CURRENT iris outline (`model.iris.outline`,
   normalized to unit radius) into a kernel of cells with uniform weight summing to 1. Splatting a per-real-
   pixel-electron value with a unit-sum kernel is energy-conserving in the sense that matters for an extended,
   locally-uniform surface: the accumulated value at any destination pixel equals the local sharp value
   (weights sum to 1, all nearby sources agree), so a flat region's brightness is unchanged by blur, only its
   sharp edges are — this is also what makes `render.test.ts`'s own noise golden test able to use the SHARP
   per-pixel electron count as the correct predicted mean even inside a blurred region.
6. **Point highlights, splatted separately** (see "Known limits" below for why).
7. **Pipeline stages**: black level -> normalize to [0,1] by the ADC's own full code range -> demosaic
   (Malvar-He-Cutler) -> white balance (`color.ts`'s `whiteBalanceGains`, under the scene's own illuminant and
   this sensor's own QE) -> color matrix (see below) -> tone curve (`pipeline.ts`'s `srgbToneCurve`) -> encode.
   `stages.{demosaic,wb,ccm,tone}` each keep the full-resolution, 3-channel-interleaved `Float32Array` for BRIEF.md
   set piece 8's scrubber.

### The color matrix: fit at a scale the real pipeline actually produces

`fitColorMatrix` fits `color.ts`'s `fitCameraToXYZ` on the 24 ColorChecker patches (real reflectances, this
sensor's real QE, the scene's real illuminant shape), composed with `XYZ_TO_LINEAR_SRGB`. Both the training
camera-RGB values (white-balanced, matching the pipeline's own stage order) and the training XYZ values are
**normalized to a spectrally-flat reference reflector** (rho = 1, mapping to white-balanced RGB = (1,1,1) and
Y = 1) before the fit. This matters: `spectrumToCameraRGB`'s raw spectral integral and the real pipeline's
normalized-[0,1]-DN input differ by several orders of magnitude, and fitting directly on the former (an
earlier version of this function did exactly that) bakes that huge, physically meaningless scale factor into
the matrix — every real rendered pixel then comes out crushed toward black once the matrix is applied to
actual (normalized) pipeline data, regardless of how well-exposed the scene is. A linear matrix's own overall
scale is otherwise arbitrary (M and M/k preserve every patch's chromaticity equally well), so anchoring both
sides at the one physically meaningful point they share — "a perfectly neutral reflector under this light" —
is what makes "fit under one scale, apply under a completely different one" come out correct: a dark scene
still renders dark and correctly colored, not black.

### Defocus-blur sizing: axial distance, not the ray's Euclidean hit distance (fixed 2026-09-28)

`traceSource`'s `depthMm` (from `scene.ts`'s `radiance()`) is the Euclidean 3D distance along the primary ray
to whatever it hit — the ray parameter `t` on a unit-length direction, so `depthMm * cosTheta === objectPoint[2]`
exactly (Pythagoras on the ray's own unit direction). `exitPupilBlurDiameterMm`'s `pointDistMm`, by contrast,
requires the AXIAL distance to the object's z-plane (see "The exit-pupil-referenced blur diameter" above). The
two agree only exactly on-axis (`cosTheta = 1`); everywhere else `depthMm` overstates the axial distance by
`1/cosTheta`, worse for wider lenses and larger field angles.

Both the main per-pixel loop and the point-highlight pass used to pass the raw Euclidean distance
(`src.depthMm`, and `projectToRenderedPixel`'s returned `depthMm`, respectively) straight into
`exitPupilBlurDiameterMm`, sizing every off-axis pixel's defocus-blur splat kernel from an overstated object
distance — measured at ~3.2% too large for an ordinary in-frame billboard hit (p50 at f/2 focused at 1 m,
pixel (300,50)/600x400) and ~13.2% too large for a background point 45 degrees off-axis. Both now pass the
hit's own already-computed axial z instead: `src.objectPoint[2]` in the main loop, the highlight's own world
`Z` (from `hl.position`, already in scope) in the highlight pass. `exitPupilBlurDiameterMm` and `pointBundle`
needed no change — both already used the axial convention correctly. `render.test.ts`'s golden point-highlight
test only ever exercised the on-axis case (world `(0,0,25000)`, where the two distances are identical by
construction), so it never caught this; see `src/engine/e4.verify.test.ts` for the off-axis regression checks
(the correct, axial-distance call compared against an independently-derived expected blur diameter, plus a
"for the record" check that the old Euclidean-distance call still measurably disagrees).

## Known limits

- **Point highlights cannot be hit by a per-pixel primary ray, and are rendered as a separate, direct-
  projection splat pass instead.** A physically small emitter (`scenes.ts`'s point highlights are a few mm)
  subtends a far smaller angle than one rendered pixel at any resolution this module targets — e.g. a 2 mm
  source at 25 m is roughly 240x narrower, in angle, than one rendered pixel at 600x400 on a 50 mm lens — so a
  single primary ray per rendered pixel has essentially zero chance of ever landing on one; a scene rendered
  purely through `traceSource`'s per-pixel sampling would simply never show its background highlights.
  `renderImage` instead projects each `PointHighlight` directly (`projectToRenderedPixel`, the exact algebraic
  inverse of `traceSource`'s own projection) to a sub-pixel-precise position and splats its own radiance
  through the same camera equation and kernel machinery, added on top of whatever the main pass already
  rendered there. This is also physically the correct composite for a source much smaller than its own blur
  footprint (a real sensor region under a defocused point light receives both the background around it and
  the point source's own contribution). A `PointHighlight`'s radiance is treated with the same
  `imageIrradiance` (extended-Lambertian-surface) formula as everything else, which is a simplification for a
  source this small (a rigorous point-source treatment would instead conserve the source's OWN total flux
  through the entrance pupil and spread that over the blur disk, rather than treating every direction within
  the disk as if the source filled that whole solid angle) — acceptable for this prototype's qualitative
  "bright, recognizably disk-shaped highlight, sized by the same physics as everything else" goal (which the
  render golden test checks directly: the disk's measured diameter against `exitPupilBlurDiameterMm` +
  diffraction), not intended as photometrically rigorous point-source radiometry.
- **The splat kernel radius is capped at `MAX_KERNEL_RADIUS_PX` (18 rendered pixels)** so a single extremely
  defocused source (a very fast lens, a very close point, a background near infinity at a long focal length)
  cannot blow the render's own time budget open (BRIEF.md: "under 3 s in node" is a hard target, checked
  directly by `render.test.ts`). Beyond the cap, a source renders slightly sharper than the true physics at
  that one location; `RenderResult.meta.notes` says so when it happens. The 600x400 target case measured
  under 2.2 s on this machine with real defocus blur present (well inside budget); the cap has not been
  observed to bind on any scenario this workstream's own tests exercise.
- **Defocus and diffraction blur are combined in quadrature (RSS) into one splat kernel**, not by a true
  convolution of the geometric defocus disk with the Airy pattern — an assumed combination rule, common in
  photographic-optics engineering estimates but not a rigorous PSF convolution. The kernel's SHAPE always
  follows the iris outline (geometric), never the Airy rings; diffraction only widens it.
- **Frame-edge energy loss**: the splat scatters each source's flux from its own screen position into
  neighboring pixels; nothing scatters IN from outside the rendered frame, so a source near the edge loses
  whatever fraction of its kernel would have come from off-frame content. A common, bounded box-filter edge
  artifact, not physical vignetting; visible only within roughly one blur radius of the frame edge.
- **`pixel(x, y)`'s spectral shape is this pixel's own sharp (unblurred) spectrum, scaled to the properly
  blurred per-channel brightness.** The main render pass collapses each source to 3 channel values for
  performance (see "Channel collapse" above), so by the time `pixel()` needs a full 16-bin spectrum for
  `sensor.samplePixel`, the per-bin blur contributions are no longer separately available; it re-traces this
  exact pixel's own sharp spectrum on demand and rescales its overall brightness (one scalar, per its own CFA
  channel) to match the already-accumulated blurred value. This keeps the well-fill level's BRIGHTNESS
  correctly blurred while the SPECTRAL detail shown is this point's own, not a true blurred spectrum — visible
  only when tapping a pixel whose neighbors are spectrally very different from it while heavily defocused
  (e.g. right at the edge of the bokeh-highlight disk against the backdrop).
- **A single representative lens transmission (`ASSUMED_LENS_TRANSMISSION = 0.9`)** stands in for every lens
  and every element/coating combination; this engine has no per-element transmission/coating data (BRIEF.md
  lists T-stop and coatings as later work). Evidence: assumed.
- **The rectilinear pinhole projection** (see "Rendering pipeline," step 1) has no entrance-pupil offset, no
  distortion, and treats the whole system as a single thin projection from the sensor through one point — a
  documented simplification BRIEF.md's own task text calls acceptable for this prototype.
- **`needs_from_lead`**: `dof.ts`'s `blurDiameter` could take an optional exit-pupil z (see camera.ts, above)
  so a real-pupil-magnification lens does not need this workstream's own `exitPupilBlurDiameterMm` reimplementation.
  `sensor.ts`'s `ReadNoiseSpec`/`fullWellAtIso` two-level (LCG/HCG) model could grow a continuous-curve variant
  (`data.ts`'s `sensorReadNoiseAtIso` already builds the real curve; camera.ts/render.ts work around the gap by
  baking one ISO's own interpolated value into both levels of a fresh `SensorSpec` per request).
