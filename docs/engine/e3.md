# E3: sensor, pipeline and scene

`rng.ts`, `sensor.ts`, `color.ts`, `pipeline.ts` and `scene.ts` in `src/engine/`, plus their fixtures in
`src/engine/fixtures/e3-*.ts`. Pure TypeScript, no Three.js, no DOM, no `data/` imports — every module takes
its sensor parameters, spectra, CMFs and illuminants as arguments (see "Data injection," below). 101 Vitest
tests, `npx tsc --noEmit -p .` clean.

This file is E3's half of the contract ENGINE.md describes: the API, the conventions, the derivations (with
citations), and the known limits. It does not restate ENGINE.md's shared conventions (units, axes,
allocation) except where E3 makes a specific choice worth flagging.

## Data injection

Nothing here imports `data/sensors.json` or `data/color/*.json`. `sensor.ts`'s `SensorSpec`, `color.ts`'s
`CMFs`/`ChannelSensitivities` and `scene.ts`'s `Illuminant`/`Billboard` are all *shapes* a caller fills in;
the lead adds `src/engine/data.ts` to bridge real data into these shapes after the E1-E3 merge. Every test
in this workstream instead uses `src/engine/fixtures/e3-cie.ts` (CIE 1931 CMFs, D65's measured SPD, the
CIE daylight S0/S1/S2 basis functions — all three pulled from primary published tables, not summarized or
guessed; see that file's header for exactly where) and `src/engine/fixtures/e3-sensor.ts` (an illustrative,
explicitly-not-a-real-datasheet `SensorSpec`).

## rng.ts — seeded randomness

```
class Pcg32 implements Rng           // PCG32 (O'Neill 2014); constructor(seed, seq = 1)
  nextUint32(): number               // raw 32-bit output
  next(): number                     // uniform [0, 1), 2^-32 resolution
  normal(): number                   // standard normal, Box-Muller
  poisson(mean: number): number      // exact Poisson, Knuth below mean 10, Hörmann PTRS above
makeRng(seed, seq = 1): Rng          // factory
```

PCG32's output stage is checked against a published reference vector (seed=42, seq=54 ->
`[2707161783, 2068313097, 3122475824, 2211639955, 3215226955]`, from
[rosettacode.org/wiki/Pseudo-random_numbers/PCG32](https://rosettacode.org/wiki/Pseudo-random_numbers/PCG32),
itself following the pcg-random.org reference C implementation) — this is the closest thing to a "golden"
test a PRNG's raw bitstream can have, since the algorithm's output *is* the specification. Poisson is
checked three ways: sample mean/variance against the exact Poisson moments at means spanning the
Knuth/PTRS crossover (0.5, 5, 50, 5000), a chi-square goodness of fit against an independently-computed
Poisson(4) pmf table, and determinism across repeated runs at a fixed seed.

State is kept as `BigInt` masked to 64 bits, not a hand-rolled 32-bit-limb multiply. This is the one
deliberate perf-vs-correctness tradeoff in E3 worth restating here: see "Known limits."

## sensor.ts — the per-pixel model

```
interface SensorSpec { pitchUm, fillFactor, qe: Record<CfaColor, nm=>QE>, fullWellE, fullWellHcgE?,
                        darkCurrentEPerS, readNoise: {lcgE, hcgE}, dcgSwitchIso, unityGainIso, bitDepth,
                        blackLevelDn, prnuStdDev, baseIso }   // local type; data/sensors.json fills it in later

expectedElectrons(sensor, photonsByBin, binCentersNm, channel): number
readNoiseE(sensor, iso): number                      // hcgE at/above dcgSwitchIso, else lcgE
fullWellAtIso(sensor, iso): number                    // fullWellHcgE at/above dcgSwitchIso if given, else fullWellE
analogGain(sensor, iso): number                      // DN/e-, = iso / unityGainIso
maxDn(sensor): number                                // 2^bitDepth - 1
readout(sensor, electrons, iso, readNoiseSample = 0): number   // deterministic: gain, black level, ADC
samplePixel(sensor, rng, params): PixelState          // the full stochastic draw (see below)

varianceE(sensor, signalE, exposureS, iso): number    // shot + PRNU + dark shot + read, e-^2
snr(sensor, signalE, exposureS, iso): number          // signalE / sqrt(varianceE(...))
engineeringDR(sensor, iso): number                    // stops, log2(fullWell / readNoise)
photographicDR(sensor, exposureS, iso, cocMm, snrThreshold = 20): number   // stops, Claff PDR
```

`samplePixel`'s order (photons -> `PixelState`): expected electrons (QE x fill factor) -> one Poisson draw
for photo-electrons (valid because Poisson thinning by QE keeps a Poisson process Poisson — see the doc
comment on `samplePixel` for the citation) -> PRNU multiplies the photo-electrons only -> an independent
Poisson draw for dark current (rate x exposure time) added in -> clip at full well (`fullWellAtIso`, this
sets `saturated`) -> read noise (Gaussian, e- rms, picked by ISO vs. `dcgSwitchIso`) -> analog gain
(`iso / unityGainIso`) -> black level -> round and clip to `[0, 2^bitDepth - 1]`.

**Per-DCG-mode full well**: `fullWellAtIso(sensor, iso)` picks `sensor.fullWellHcgE` at/above
`dcgSwitchIso` when the sensor spec gives one, else `sensor.fullWellE` in both modes (same LCG-below/
HCG-at-or-above split as `readNoiseE`). `engineeringDR`, `photographicDR` and `samplePixel`'s clip/
`saturated` all go through it. This exists because dual conversion gain is a physical tradeoff, not just a
read-noise change: switching to a smaller floating-diffusion sense-node capacitance in HCG mode is what
raises the charge-to-voltage conversion gain (lowering read noise, `ReadNoiseSpec.hcgE`'s own doc comment)
*and* lowers full well (Q = C*V, a smaller capacitance holds fewer electrons at the same voltage swing) — the
same switch, two consequences. `fullWellHcgE` is optional (defaulting to `fullWellE`) so existing/
placeholder `SensorSpec` values (including this workstream's own `FIXTURE_SENSOR`, which does not set it)
keep behaving exactly as before; a real per-mode full well arrives with `data/sensors.json` after the merge,
same as every other `SensorSpec` field (see "Data injection," above). `sensor.test.ts`'s
`fullWellAtIso`/DCG-full-well tests cover the split and the DR/`samplePixel` consequences.

**Deviation from ENGINE.md's literal stage order, flagged for the lead:** ENGINE.md lists the stages as
"...Poisson draw -> dark current (Poisson of rate\*t) -> PRNU multiplier -> full-well clip...", which reads
as PRNU multiplying the *combined* photo+dark signal. This module instead applies PRNU to the
photo-electrons only, before summing in dark current. Reasoning: PRNU (photoresponse non-uniformity) is
specifically a per-pixel gain variation in converting photons to electrons (Janesick 2007, ch. 4); dark
current has its own, separate non-uniformity (DSNU, dark signal non-uniformity), not modeled by this
module (see "Known limits"). Applying one multiplicative factor to both conflates two different physical
effects, and — more importantly for testability — it would make the analytic `varianceE`/`snr` formulas
(which use the standard Janesick decomposition, PRNU-on-signal-only) disagree with what `samplePixel`
actually draws. If the lead wants the literal ENGINE.md order instead, it is a one-line change in
`samplePixel` (multiply after summing dark current) plus a matching change to `varianceE`'s derivation.

Golden formula check: with every noise source but shot noise zeroed (`SHOT_NOISE_ONLY_SENSOR` in the
sensor fixture), `snr(...)` reduces to exactly `sqrt(signalE)` — BRIEF.md's own accuracy-discipline
checklist names "shot-noise SNR = sqrt(N)" explicitly; `sensor.test.ts` checks it directly.

**Photographic Dynamic Range**: `photographicDR` implements Bill Claff's PDR as documented at
[photonstophotos.net's Sensor Analysis Primer](https://www.photonstophotos.net/GeneralTopics/Sensors_&_Raw/Sensor_Analysis_Primer/Engineering_and_Photographic_Dynamic_Range.htm)
(retrieved 2026-09-28): not an SNR=1 floor (that is `engineeringDR`) but a higher SNR threshold evaluated
after averaging over a circle-of-confusion-sized patch (noise over N pixels averages down by sqrt(N), the
standard result, so the per-pixel SNR needed is `snrThreshold / sqrt(N)`). Claff's own threshold scales
with output resolution (`16000 / picture-height-px`, asymptoting to a flat SNR=1 for very tall images and
to about SNR=20 for a ~800px-tall output); this module takes a flat `snrThreshold = 20` as a simpler,
documented stand-in, since the picture-height-scaled version needs a rendered image's dimensions, which
this module doesn't have — the lead or a UI layer can pass a different `snrThreshold` derived from the
actual output size if that resolution-dependent behavior matters.

## color.ts — spectra, XYZ, sRGB, camera color

```
type Mat3 = readonly [9 numbers]                      // row-major
mat3Vec3, mat3Multiply, mat3Invert(m): Mat3            // shared with pipeline.ts's color-matrix stage

spectrumToXYZ(spectrum, bins, cmfs): Vec3              // raw radiometric tristimulus integral
reflectanceToXYZ(reflectance, illuminant, bins, cmfs): Vec3   // Y=100-normalized object-color XYZ
spectrumToCameraRGB(spectrum, bins, sens): Vec3

LINEAR_SRGB_TO_XYZ, XYZ_TO_LINEAR_SRGB: Mat3           // IEC 61966-2-1
linearSrgbToXyz, xyzToLinearSrgb(v): Vec3
srgbEncode(c), srgbDecode(c): number                   // sRGB OETF/EOTF, c in [0,1]

fitCameraToXYZ(cameraRGB: Vec3[], xyz: Vec3[]): Mat3   // least squares (normal equations)
whiteBalanceGains(illuminant, bins, sens): Vec3        // gain-to-neutral, normalized to G=1
```

The `Bins` integration convention used throughout (here and in `scene.ts`): `integral ~= sum_i f(centers[i])
* weights[i]`, a midpoint/rectangle rule over each bin's width — matching how `types.ts` documents
`Bins.weights` ("bin widths or quadrature weights").

`LINEAR_SRGB_TO_XYZ`/`XYZ_TO_LINEAR_SRGB` are cross-checked against each other (`mat3Invert` of one should
equal the other) and against the D65 white point (`linearSrgbToXyz([1,1,1])`'s chromaticity should be
D65's (0.3127, 0.3290)) in `color.test.ts`, rather than re-derived from the sRGB primaries by hand — the
nine-digit coefficients are the commonly-reproduced solution of that primaries system (IEC 61966-2-1), and
re-deriving them independently would mostly test floating-point arithmetic, not this module.

`reflectanceToXYZ` is checked against the actual published D65 white point (X=95.047, Y=100, Z=108.883,
CIE 15:2004 / Schanda 2007) via the CMF+D65 fixtures, at 0.5% tolerance (the 10 nm quadrature was measured
numerically at about 0.03-0.07% relative error against that target — see the derivation note in
`fixtures/e3-cie.ts`).

## pipeline.ts — mosaic to photo

```
interface Plane { width, height, data: Float32Array }
type BayerPattern = 'RGGB' | 'BGGR' | 'GRBG' | 'GBRG'
cfaColorAt(pattern, x, y): CfaColor

blackLevelSubtract(raw, blackLevelDn): Plane
demosaicBilinear(raw, pattern): RgbPlanes
demosaicMalvarHeCutler(raw, pattern): RgbPlanes        // falls back to bilinear inside its 2px border
applyWhiteBalance(planes, gains: Vec3): RgbPlanes
applyColorMatrix(planes, m: Mat3): RgbPlanes
srgbToneCurve = srgbEncode                             // re-exported from color.ts
acesFilmicToneCurve(x): number                         // Narkowicz 2016 filmic fit
applyToneCurve(planes, curve): RgbPlanes
encodeRGB8(planes): { width, height, data: Uint8ClampedArray }
bilateralFilter(plane, {spatialSigma, rangeSigma, radius?}): Plane
gaussianBlur(plane, sigma): Plane
unsharpMask(plane, {sigma, amount}): Plane
```

Every stage takes and returns `Plane`s (or `RgbPlanes`, three of them), so a caller can run any subset in
any order — set piece 8 in BRIEF.md ("From mosaic to photo... each stage a visible transformation you can
scrub back and forth") wants exactly this. `cfaColorAt` reads a `BayerPattern` string's four characters as
`TL,TR / BL,BR`, so `demosaicBilinear` and `demosaicMalvarHeCutler` are written once and work for all four
patterns, rather than four hand-coded cases each.

**Malvar-He-Cutler kernels**: the five 5x5 filters from Malvar, H. S., He, L.-W. & Cutler, R., "High-Quality
Linear Interpolation for Demosaicing of Bayer-Patterned Color Images," ICASSP 2004, reproduced from the
numeric tables in [colour-demosaicing](https://github.com/colour-science/colour-demosaicing)
(`colour_demosaicing/bayer/demosaicing/malvar2004.py`), retrieved 2026-09-28 — the standard open-source
reference implementation of this algorithm. **Golden test, exactly as ENGINE.md asks**: every MHC kernel
(and every bilinear tap set) is spatially symmetric under `kx -> -kx` and `ky -> -ky`, and its taps sum to
8; a symmetric, DC-normalized kernel reproduces any locally linear function `a*x + b*y + c` exactly (its
first spatial moment is zero), which `pipeline.test.ts` checks directly against a synthetic ramp, away from
each algorithm's own border (1px for bilinear, 2px for MHC).

Border policy: `demosaicBilinear` averages whatever same-colored neighbors are in bounds (fewer at the
edge, so not ramp-exact there); `demosaicMalvarHeCutler` falls back to the bilinear result inside its
2-pixel margin rather than attempting a clipped/renormalized kernel there.

## scene.ts — synthetic scenes

```
interface Billboard { id, center, normal, up, widthMm, heightMm, reflectanceAt(u,v): nm=>number }
interface PointHighlight { id, position, radiusMm, radianceAt: nm=>number }
interface Scene { billboards, pointHighlights?, illuminant: {spectrum, lux} }

illuminantSpectralIrradiance(spectrum, lux, bins, vLambda): nm=>number
planckianSpectralRadiance(nm, tempK): number
daylightChromaticity(cctK): {x, y}                     // valid 4000-25000 K
daylightSpd(cctK, s0, s1, s2): number[]
siemensStarReflectance(spokes, high, low): (u,v)=>nm=>number
radiance(scene, rayOrigin, rayDir, bins, vLambda): { radianceByBin, depthMm, hitId }
```

`u, v` on a `Billboard` are fractions of `widthMm`/`heightMm` in `[-0.5, 0.5]` from center, so
`reflectanceAt` can carve up one billboard into a ColorChecker's patches, a Siemens star
(`siemensStarReflectance`), or anything else region-dependent, without this module needing a dedicated type
per scene content.

**`u`-axis sign**: the local "right" axis (increasing `u`) is `normalize(cross(bb.normal, bb.up))`, i.e.
`normal x up`, not `up x normal`. For a camera-facing billboard (`normal` pointing back against the
incoming ray, e.g. `normal=[0,0,-1]` for a ray traveling `+z`, per this module's own doc comment on
`Billboard.normal`) this makes `u` increase toward world `+x`, matching `types.ts`'s right-handed x,y,z
convention (`x_hat x y_hat = z_hat`) with `forward = -normal`, `up = +y`: solving `right x up = forward`
gives `right = +x`. Getting the operand order backwards silently mirrors every spatially-varying
`reflectanceAt` left-right (a ColorChecker layout, a Siemens star) without failing any bounds/hit test,
since `|u| > 0.5` is unaffected by `u`'s sign — see `e3.verify.test.ts`'s FINDING 1 and `scene.test.ts`'s
Siemens-star/edge-of-billboard tests, whose own inline comments state the intended `+x` sign but never
assert it.

**Lambertian reflection**: `L = rho(lambda) * E(lambda) / pi`, from the ideal-diffuse BRDF `f_r = rho/pi`
(standard radiometry, e.g. Pharr, Jakob & Humphreys, "Physically Based Rendering," 4th ed., 2023, §5.6.1 /
§4.1). `E` (the scene's illuminant irradiance) is uniform over every surface in the scene — see "Known
limits."

**Lux -> spectral irradiance**, the specific thing ENGINE.md asks this module's tests to check against the
V(lambda) integral: `illuminantSpectralIrradiance` normalizes a relative spectral shape so that
`Km * integral(E(l) * V(l) dl) = lux` exactly (`Km = 683` lm/W, the CIE 1924 photopic luminous efficacy at
555 nm, exact by the SI definition of the candela; CIE 018:2019, "The Basis of Physical Photometry").
`scene.test.ts` checks this two ways: directly (construct `E`, integrate it back through `V(lambda)`,
recover the original lux), and end-to-end through `radiance()` on a perfect (`rho=1`) diffuser, where the
Lambertian relation inverts to `E = pi * L` and the same integral should still recover the scene's stated
lux. `CIE1931_YBAR` (from the CMF fixture) is reused as `V(lambda)`: the CIE Y tristimulus curve was
defined to track luminance, so `ybar` *is* the CIE 1924 photopic luminous efficiency function (CIE 15:2004,
§3.3.3) — no separate `V(lambda)` fixture table is needed.

**CIE daylight locus**: `daylightChromaticity`/`daylightSpd` implement the Judd-MacAdam-Wyszecki (1964)
daylight-locus formula. `daylightSpd` is checked against the real, measured CIE D65 SPD table at D65's own
(precise, "rectified") CCT of 6503.51 K — two independently-published tables (the S0/S1/S2 basis functions,
and D65's own adopted SPD) agreeing to within 0.5% is a strong check that the formula, not just the test's
internal consistency, is right (a numeric check while building the fixture found agreement to about 5e-6
relative at that exact CCT — see `fixtures/e3-cie.ts`).

`planckianSpectralRadiance` returns SI units per meter of wavelength, not per nm, on purpose: only the
*shape* of an illuminant spectrum matters to `illuminantSpectralIrradiance` (its absolute scale is
renormalized away by the lux target), and the per-meter-to-per-nm conversion is a wavelength-independent
constant (1e-9), so it cancels and doesn't need to be applied. Checked against Wien's displacement law
(`lambda_max * T = 2.897771955e-3 m.K`, CODATA/SI-exact) by a direct numeric peak search over the function,
independent of the formula's own derivation.

## Known limits

- **rng.ts uses `BigInt`** for PCG32's 64-bit state, not a 32-bit-limb reimplementation. This is exact and
  easy to audit (the golden test above pins it precisely), but likely slower than a hand-rolled 64-bit
  multiply-add would be, at whatever scale a full-frame Monte Carlo render eventually needs. If sampling
  throughput becomes the bottleneck, the fix is a no-BigInt `step`/`nextUint32` reimplementation checked
  against this file's reference vector before it replaces the BigInt version — not a new algorithm.
- **PRNU is applied to the photo-electron signal only**, not to dark current (see sensor.ts's deviation
  note above). Real sensors also have dark-signal non-uniformity (DSNU), a separate per-pixel fixed-pattern
  effect on the dark current specifically; this module does not model DSNU at all (dark current is treated
  as spatially uniform in its mean, only shot-noise-random pixel to pixel).
- **`samplePixel`'s per-call allocations**: it slices `photonsByBin` into the returned `PixelState` and
  allocates that object itself. Fine for the loupe's single-pixel-at-a-time use (BRIEF.md set piece 9) or
  for building images off the CPU reference renderer; a full-frame hot path that doesn't need the per-bin
  detail should call `expectedElectrons` directly and skip `samplePixel`'s bookkeeping.
- **`pipeline.ts`'s stages each allocate a full new `Plane`/`RgbPlanes`** rather than writing in place.
  This favors the explicit "composable, scrubbable stages" request in BRIEF.md/ENGINE.md over the
  allocation-free guidance, which this module reads as being about inner per-sample loops (`rng.ts`,
  `sensor.ts`) rather than the once-per-frame stage boundaries here. An in-place variant of any given stage
  is a straightforward follow-up if a full-resolution interactive scrubber needs it.
- **`scene.ts`'s illuminant is uniform over the whole scene**: no shadows, no cosine-of-incidence falloff
  from a directional source, no inverse-square falloff for the main illuminant (only `PointHighlight`s,
  which are direct emitters rather than reflectors, have their own finite size/position). This matches
  ENGINE.md's ask for `radiance(scene, ray) -> spectral radiance per bin and depth` as the primitive a
  renderer calls per sample — per-surface shading detail (shadowing, multiple bounces, non-uniform
  lighting) is a rendering-layer concern E3 was not asked to model.
- **`photographicDR`'s `snrThreshold`** defaults to a flat 20 rather than Claff's actual
  resolution-scaled `16000 / picture-height-px` (see color.ts section above) — this module has no picture
  height to scale by.
- **`daylightChromaticity`/`daylightSpd`** are only valid for the published locus's stated range, 4000-25000
  K (enforced by a thrown `RangeError`); a scenario wanting a lower/higher CCT needs a different model
  (e.g. pure Planckian, via `planckianSpectralRadiance` directly) below/above that range.
