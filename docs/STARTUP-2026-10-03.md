# Workspace startup measurement — 10/3/2026

The reported eight-second wait did not reproduce on this machine. The existing workspace still serialized two independent operations: graphics initialization completed before the first photo worker started. Starting that same render immediately after the store is created lets it overlap graphics initialization. The UI takes its pending or completed promise once, then paints and publishes it normally. No image resolution, random seed, sample count, physics, materials, or camera framing changed.

## Measurements

Production Vite build served locally; Windows Chrome headless, WebGPU/D3D11, reduced motion. Desktop viewport 1366 × 900; phone-sized viewport 390 × 844 on the same desktop hardware. Cold means a fresh browser context/HTTP cache; warm means reloading that context. These are one sample per condition, not physical-phone or network-throttled results. GPU/driver caching and machine load affect these numbers.

| Viewport/cache | Controls ready, before → after | First GPU-complete usable frame | First RAF observing published photo |
| --- | --- | --- | --- |
| Desktop, cold | 2.65 → 2.24 s | 3.33 → 2.52 s | 5.58 → 2.11 s |
| Desktop, warm | 1.55 → 1.92 s | 2.07 → 2.30 s | 4.23 → 2.28 s |
| Phone size, cold | 2.38 → 2.12 s | 3.24 → 2.67 s | 5.25 → 2.03 s |
| Phone size, warm | 1.62 → 1.58 s | 2.13 → 2.00 s | 4.20 → 1.99 s |

The cold camera frame improved in both viewports. Warm desktop camera timing increased by 0.22 s in this single sample, while the photo appeared 1.94 s sooner. This is a parallel-startup improvement, not a claim that every individual resource is faster.

The baseline desktop worker starts at 2.34 s and replies at 3.82 s; with overlap it starts at 0.16 s and replies at 1.33 s. The photo RAF marker additionally includes UI mounting/publication and browser frame scheduling; it is not the worker's compute duration. Baseline Draco decoding spans about 115–123 ms, so replacing the decoder is not justified by this local measurement. The baseline cold DSLR/lens downloads complete in about 70 ms; the decoder script adds about 185 ms desktop or 14 ms phone-sized. Remote network costs remain unmeasured.

## Integration

The opening-photo workstream owns the entry point. Immediately after `createStore()` and before `await createStage(dom)`, it calls:

```ts
const photo = byId<HTMLCanvasElement>('finalimg-canvas');
prewarmInitialRender(store.get().scenario, photo.width, photo.height);
```

Import `prewarmInitialRender` from `./app/render-client` in `src/app-start.ts`. The benchmark temporarily used the identical call in the original `src/main.ts`; that temporary edit was removed from this workstream so the new entry point has one owner. Both changes must be integrated before expecting the measured improvement. A bare-page photo opening is a separate first-content metric; this gate explicitly opens `?piece=camera&lens=n50`.

The handoff is keyed by normalized scenario, image dimensions, and seed. A changed request supersedes the prepared render. Worker crashes clear the handoff, a failed preload cannot cause an unhandled rejection, and no result is published before the UI paints it. Subsequent slider/selection behavior keeps the existing latest-wins queue.
